一句话说清
一个面向学习场景的视频内容理解 + 个性化推荐平台：用户上传教学视频，系统自动转码成 HLS、用 ASR 转写 + 大模型摘要 + 向量化把视频切成"带语义标签的知识点片段"存进 pgvector；学习者输入一道题 / 一个知识点，系统按语义向量召回最相关的视频片段，或像刷短视频一样连续获得个性化推荐；所有观看/点赞/评论行为回流，驱动 RecBole 双塔模型离线训练，形成"数据→训练→发布→推荐→回流"的闭环。

它解决的真实问题

  • 长视频"找不到要看的内容"：一门课一小时，学生只想看某个知识点那 3 分钟 → 用语义切割把视频拆成可定位的片段。
  • "按题找课"的检索需求：学生拿一道题/一个知识点去匹配讲解 → 向量召回代替关键词匹配。
  • 个性化冷启动：新用户没有行为 → 用题目向量 + 知识图谱弱项召回兜底；有行为后用双塔模型。
  • 推荐质量可验证：不是拍脑袋推荐，用曝光-反馈数据离线评估（Recall@20 / NDCG@20）并做模型门禁发布。
注：这是仓库级多项目容器，对外服务入口是 video-service（Go HTTP API + worker），推荐用 REST 对接。

分层清晰：接入层 → 应用层 → 基础设施层 → 异步 worker，DDD 风格 + 接口适配器

④ 领域与基础设施层（internal/domain + internal/infrastructure）
domain/video 领域模型；infrastructure 含 AI(LLM)、embedding、transcode(FFmpeg)、objectstorage(RustFS/S3)、persistence(GORM+pgvector+recsys schema)、redis(队列+缓冲)。
⑤ 异步 worker（cmd/worker + internal/worker）

⑥ 数据与外部依赖

设计要点：为什么两套向量？

1536 维：edu_video_segment.embedding / edu_user_video_profile.profile_vector，来自 DashScope text-embedding-v4，用于语义召回（题目↔片段、画像↔片段）。
64 维：recsys.*_embedding，来自 RecBole 双塔 BPR 训练产出，保留点积语义，用于个性化模型召回。维度小、检索快，专为线上 pgvector 检索设计。

索引与迁移工程

  • 向量索引：ivfflat (embedding vector_cosine_ops) lists=100 —— 余弦距离近似最近邻。
  • 评论：(video_segment_id, root_id, create_time) 复合索引 + 回复部分索引 WHERE parent_id <> 0。
  • 迁移：启动时 CREATE EXTENSION vector + AutoMigrate + 幂等建索引，用 PostgreSQL advisory lock 保证 HTTP 与 worker 多进程并发迁移不冲突。

4核心机制拆解

4.1 异步任务体系（Redis 队列 + 多级流水线）

所有重活异步化，Redis 承载队列与缓冲：

队列/缓冲用途
video:transcode:queue视频转码任务（BRPOP 消费，超时回收）
video:vector:{prepare|coarse|refine|finalize}向量化四级流水线队列
knowledge_video:transcode:stream知识点视频转码（Redis Stream）
video/segment:reaction:queue、comment:like:queue点赞/反应缓冲：先写 Redis 计数，worker 异步刷库，扛高并发点踩
video:random_play:recent/bucket随机播放去重（30min）与推荐桶预取
video:runtime:active运行时活跃计数（监控指标）

4.2 视频向量化：分层切割（核心亮点）

Prepare取视频、探时长
→
Coarse 粗切40s 基础分片
ants 协程池 12 并发
裁剪+上传+粗ASR
→

→

落库片段+标签
  • 为什么滑动窗口步长 < 窗口（30s/20s）：相邻窗口产生重叠分析区，避免关键句被硬切点切断，保证语义完整性。
  • 结尾对齐：结尾顺延 ≤6s 收全语句，探测步长 0.5s，避免片段末尾"说一半"。
  • 协程池流水线：裁剪→上传→ASR 三个阶段用 ants 协程池 + channel 流水线并行，互不阻塞；每段都有超时（12min/10min）。
  • 幂等 & 可重试：edu_video_vector_stage 唯一约束防重复处理，失败记录 error_message/retry_count，支持断点续跑。
  • AI 降级：AI provider 不可用时进入 degraded 模式（保留基础上传/播放，跳过向量化），核心服务不挂。

4.3 推荐系统：三引擎热切换

配置项 Recommendation.Engine 可切换 knowledge_match | gorse | recbole，当前线上 recbole。

策略机制典型场景
question_vector题目 → embedding(1536) → pgvector 余弦召回片段，score=1/(1+distance)按题找讲解
knowledge_match结合用户画像向量 + 知识弱项召回（weak knowledge），先画像 rerank（≤300 候选）随机播放兜底
profile_rerankquestion 候选 + 用户画像向量二次打分排序个性化排序
recbole离线双塔 BPR 产出 64 维 user/item embedding → pgvector 检索个性化主推
gorseGorse 协同过滤（feedback 同步 + 候选集），RecBole 可作 external recommender 提供候选 ID可选集成

随机播放桶：不每次现算，按用户把推荐结果预取进 Redis 桶（min 3 / max 5），弹出即播，配合 30min 去重，既快又不过度重复。

4.4 训练闭环：RecBole 双塔 + 门禁发布

  1. 取数：export_recbole_dataset 导出 .inter（显式交互 + 观看/曝光 + 题目搜视频行为）、.user（画像/答题/搜索特征）、.item（片段+内容元数据）。
  2. 训练：RecBole BPR，embedding_size=64，uniform 负采样，eval NDCG@20，8:1:1 切分。
  3. 评估 & 门禁：产出 Recall@20 / NDCG@20 / Hit@20 / Precision@20，与当前激活版本基线对比，不达标不发布。
  4. 发布：import 新 embedding 到 recsys schema，切换 model_version 为 active，旧版本保留可回滚。
  5. 回流：曝光表记录 strategy/model_version，为下一轮训练积累样本。

4.5 互动与评论的并发设计

  • 点赞/反应走 Redis 缓冲：写请求只操作内存计数，worker 异步合并落库，防抖+扛量。
  • 两级评论（root/parent）+ 部分索引，回复列表按时间倒序分页。

5面试深挖 TOP 20（标准答案 + 深入解析）

面试官最可能从这些点切入，每个问题给出"标准答案"和"再往深问一层"的解析
Q1 为什么用 pgvector 而不是专门的向量数据库（Milvus/FAISS/Qdrant）？
标准答案：数据规模是教学视频片段，量级不大；pgvector 把向量检索和业务数据放在同一套 PostgreSQL 里，不用引入额外组件、不需要数据同步、能用事务保证一致，运维成本最低。项目还在联调/早期阶段，选型以简单可靠优先。
深入：面试官可能追问"什么时候该换向量库？"——候选量到百万级以上、需要 HNSW 高性能、或需要独立扩展/横向扩容时，才考虑专用库。pgvector 的 ivfflat 建立索引慢、召回质量略低于 HNSW，但有 hnsw 索引可选。
Q2 ivfflat 和 HNSW 的区别？你项目为什么用 ivfflat？
标准答案：ivfflat 用倒排索引把向量聚类（lists=100 个聚类中心），查询只搜最近几个簇，快但有精度损失、建索引慢、数据插入会漂移；HNSW 是分层小世界图，召回精度高、查询快，但内存占用大、构建慢。项目用 ivfflat 是默认保守选择，量小够用。
深入：可以主动说"如果数据增长我会切 HNSW"，体现你对索引特性的理解。cosine 距离 vs L2 的选择也要能说清（文本语义向量通常余弦更稳，因为只关心方向不关心模长）。
Q3 视频向量化为什么用"分层切割 + 滑动窗口重叠"？
标准答案：直接用固定时长硬切会把完整语句切断，导致片段语义残缺。方案是粗切（40s）→ ASR 拿到文本 → 细切：细切用 30s 窗口、20s 步长产生重叠区，保证句子完整；再配合结尾顺延对齐（最多 6s）收全尾部语句。这样切出来的片段能对应到清晰的知识点。
深入：能谈"粗切目的"：粗切先做初筛（哪段有有效语音、哪段是静音/片头片尾），细切只在有效区间做精标，节省 ASR 成本。ASR 是实时 FunASR WebSocket，8 路并发。
Q4 双塔模型怎么理解？BPR 损失是什么？
标准答案：双塔 = 用户塔（user_id→embedding）+ 物品塔（item_id→embedding），各自编码，最后点积/余弦得到匹配分，适合大规模线上检索（user/item embedding 可以离线算好存向量库）。BPR（Bayesian Personalized Ranking）是成对排序损失：对每个用户，正样本（看过的）得分要比随机负样本高，目标函数最大化 ln σ(x_ui - x_uj)。
深入：项目用 RecBole 的 BPR，embedding_size=64，负采样 uniform sample_num=1。能讲清"为什么要负采样""为什么双塔天然适合做召回而不是精排"（点积预计算 → 向量索引 ANN 检索）就是加分项。
Q5 冷启动怎么解决？
标准答案：三层兜底：① 内容侧：按题目向量语义召回，新用户输入题/知识点就能拿到结果；② 知识侧：知识弱项（weak knowledge）召回——从用户答题/画像推断薄弱知识点，推对应片段；③ 随机播放桶：没画像时先随机推优质片段（is_recommend 标记），积累行为后再逐步切到个性化模型。
深入：随机播放去重（30min、bucket 预取）本质是"探索+控制重复度"，可以和 EE（Exploration-Exploitation）思想挂钩。
Q6 推荐系统的评价指标你怎么看？
标准答案：离线用 Recall@K、NDCG@K、Hit@K、Precision@K：Recall 看"该推荐的有没有推出来"，NDCG 看"推荐顺序对不对"（位置加权），Hit 看"有没有命中"，Precision 看"推的对不对"。项目用 NDCG@20 作为验证主指标。
深入：能补充"离线指标 ≠ 线上效果"：离线 NDCG 高不代表 CTR 高，真正的验证要靠 A/B 或线上曝光-点击回流数据——项目里的 edu_recommend_exposure 就是为这个设计的数据闭环。
Q7 模型怎么发布上线？怎么保证不劣化？
标准答案：训练 → 评估 → 门禁（新模型指标 vs 当前激活版本基线，不达标拒绝）→ 导入 embedding 到 recsys schema → 切换 model_version 为 active → 线上按 active 版本取向量检索。旧版本保留在 recommend_model_version，可回滚。
深入：这就是"模型版本管理 + 灰度/回滚"的思想，推荐系统工程化的关键一环，比只会训练模型更能体现工程能力。
Q8 为什么有 1536 维和 64 维两套向量？
标准答案：1536 维来自通用文本 Embedding 模型（text-embedding-v4），语义丰富，用于内容理解与语义召回（题目↔片段、画像）；64 维来自 RecBole 双塔训练，是为推荐优化的专属向量，保留点积语义、维度小检索快。两者分工不同：一个"懂内容"，一个"懂用户偏好"。
深入：这体现"通用模型 + 业务模型"两层设计，是很多推荐系统的标准做法。
Q9 Redis 在项目里除了缓存还做了什么？
标准答案：它其实是项目的异步基础设施：① 队列（转码/向量化四级流水线/知识点转码 Stream）解耦重任务；② 计数缓冲（点赞/反应先写 Redis，worker 异步刷库）扛高并发互动；③ 随机播放去重与推荐桶；④ 运行时活跃指标。
深入：能说清"为什么不直接写库"（DB 写放大、热点行锁竞争）和"缓冲的最终一致性"（短暂不一致可接受，worker 兜底刷库）就是加分。
Q10 转码和向量化的失败怎么处理？
标准答案：三件套：① 任务状态持久化（edu_video_vector_stage 记录 stage/status/retry_count/error_message），进程重启可续跑；② 队列任务超时回收（pending 超过阈值重新入队）；③ 单段失败只标记该段，不影响整批；AI 服务不可用走降级模式。
深入：可展开"幂等"：唯一约束 (task_id, stage, segment_index) 防止重复处理，这是分布式任务最常见的坑。
Q11 多进程并发启动，Schema 迁移怎么做安全？
标准答案：HTTP 和 worker 可能同时启动都触发 AutoMigrate，用 PostgreSQL advisory lock（pg_advisory_lock 固定 ID）把迁移包在事务里串行化，后到者等待，避免 DDL 竞争。
深入：能对比"advisory lock vs 应用层分布式锁（Redis/DB 锁表）"的取舍，说明为什么 Postgres 自带锁最可靠。
Q12 用 ants 协程池解决什么问题？
标准答案：向量化粗切阶段每个视频要切几十段并行做"裁剪→上传→ASR"，直接开 goroutine 会无上限爆炸。用 ants 协程池固定并发（clip 12 / ASR 8），配合 channel 做三阶段流水线，控制资源、限流背压，避免打爆 FFmpeg 进程和对象存储。
深入：可以谈"为什么要池化而非每次 new goroutine"（goroutine 栈开销小但无界，池化提供上限与复用）、context 超时取消（每段 12min 超时）防止卡死。
Q13 前端是怎么组织的？和你的后端怎么对接？
标准答案：两个前端：hls-web 是开发/联调控制台（视频工作区做上传/转码/播放/系统指标，推荐工作区做诊断/预览/追踪，知识点视频工作区做批量导入），short-video-web 是产品形态的抖音风格端（上下滑 Feed、手势、两级评论）。都通过 REST API + JWT 对接，Vite 代理 /api、/videos、/swagger。
深入：能说明"控制台与产品端分离"的价值——开发期用控制台调试推荐质量、排查问题，产品端保持干净。
Q14 推荐接口按题召回和随机播放的差异？
标准答案：按题召回（by-question）是主动检索：用户明确带着题目/知识点，走语义向量召回，命中相关性优先；随机播放（random-play）是被动推荐：无明确意图，走画像/双塔/弱项召回，考虑去重和探索。两者曝光都落库。
深入：这是"检索 vs 推荐"两种场景的经典区分，能说清就说明你真的理解业务。
Q15 Gorse 在项目里是什么角色？
标准答案：Gorse 是开源的 Go 推荐系统，做协同过滤。项目把它作为可选引擎：同步反馈数据（Feedback）、用候选集召回，甚至把 RecBole 作为它的 external recommender 提供候选 ID。当前主推已切到 RecBole，Gorse 保留为可选集成。
深入：能说明"推荐引擎可插拔"的架构思想——通过统一的 Service 接口抽象，Engine 配置切换，不同模型互不侵入。
Q16 曝光数据怎么用于训练？
标准答案：每次推荐落 edu_recommend_exposure（request_id/rank/score/strategy/model_version），用户点击/观看后回写 clicked/watched + 时间戳。导数据集时把这些"曝光+反馈"作为样本，正样本=看了/点了，负样本=曝光未点，喂给 RecBole 训练。这保证了训练分布与线上分布一致。
深入：能提到"曝光-点击负样本采样（避免全库随机负样本偏差）"就是非常专业的点。
Q17 项目里怎么保证接口与文档一致？
标准答案：用 swaggo 注解生成 Swagger（docs/swagger），路由挂 /swagger/index.html，前端和 Java 对接方直接看文档联调；Swagger 是生成物不手工改。
深入：体现工程规范意识，很多候选人忽略了 API 文档化。
Q18 上传大文件/压缩包怎么做的？
标准答案：支持单文件、ZIP 归档（批量解压入库，限制展开大小 4GB/单文件 512MB/最多 1000 个）、以及分片上传：Initiate → 逐 chunk PUT → Complete 合并，前端保存断点进度，失败可续传。
深入：分片上传是面试高频题，能说清"为什么分片"（网络容错、并发上传、大文件内存友好、断点续传）就够。
Q19 知识点视频批量导入的流程？
标准答案：上传 ZIP（视频）+ XLSX（知识点映射表）→ 记录 batch → 逐条校验/入队（Redis Stream）→ worker 转码为 HLS → 关联到知识点 → 前端可查进度（total/ready/failed）和按知识点播放。
深入：这是"内容导入管线"的通用模式：批量任务要有状态机、进度、失败重试。
Q20 这个项目如果让你重构/改进，你会做什么？
标准答案：三到四个务实方向：① 向量索引从 ivfflat 切 HNSW（数据增长后）；② 推荐评估补线上 A/B 或 CTR 回流指标，不只靠离线 NDCG；③ 队列从 Redis List 升级到更可靠的消息队列（或加 DLQ/重试拓扑，仓库已有 dlqctl 工具）；④ 向量化加"增量/去重"避免重复 ASR 成本；⑤ 分片/切片的存储加生命周期管理（冷热分层）。
深入：主动暴露可改进点并给出优先级，比"项目很完美"更让面试官信服。

6简历怎么包装（STAR + 量化）

项目名建议写"衡桃学堂视频服务 · 教育视频向量化与智能推荐系统"，突出后端工程 + 推荐系统双线
示例简历条目（可直接改）

教育视频向量化与智能推荐系统（Go / PostgreSQL+pgvector / Redis / FFmpeg / RecBole）

  • 独立设计并实现视频内容理解流水线：上传 → FFmpeg HLS 转码 → FunASR 转写 → 分层语义切割（滑动窗口重叠+结尾对齐）→ 大模型摘要 → 1536 维 Embedding 入库，支撑按题向量召回；基于 ants 协程池做三阶段并行，单视频向量化任务并发可控。
  • 搭建多策略推荐系统：实现 knowledge_match / Gorse / RecBole 三引擎热切换，覆盖题目向量召回、用户画像 rerank、双塔模型召回；Redis 随机播放桶预取 + 30min 去重，冷启动分层兜底。
  • 构建推荐训练闭环：导出曝光-行为样本 → RecBole BPR 双塔离线训练 → Recall@20/NDCG@20 门禁评估 → 模型版本管理与回滚，embedding 落 recsys schema 供线上 pgvector 检索。
  • 设计异步任务与高并发互动：Redis 队列承载转码/四级向量化流水线；点赞反应 Redis 缓冲异步刷库；两级评论；PostgreSQL advisory lock 防并发迁移；全链路单测覆盖。

话术要点

  • 开场 30 秒："这是一个把教学视频变成可检索、可推荐的知识库的系统。我负责后端全链路：内容理解流水线、推荐系统、以及数据闭环。"
  • 数字随时能报：4.2 万行 Go、13+ 表、3 引擎、4 级流水线、1536/64 双向量。
  • 主动抛钩子：讲完架构后主动说"这里我最想聊的是推荐闭环——曝光数据怎么回流训练、模型怎么门禁发布"，引导面试官往你准备最充分的点问。
  • 承认边界：数据量是联调级别、没有真实线上大规模验证——但要立刻补上"所以我设计了可扩展的方向（HNSW、A/B、MQ）"，把短板转成思考深度。

7短板与应对（面试官可能的质疑）

可能的质疑怎么应对
数据量小没经过真实大规模流量承认是早期/联调阶段，但强调工程结构是按大规模设计的：异步解耦、队列缓冲、协程池限流、幂等、模型版本门禁——这些正是大规模系统需要的骨架。
单人项目是不是你一个人写的？说清你负责的核心范围（后端 + 推荐链路），其余（前端控制台、部署包）是配合完成；强调你自己把端到端打通了。
推荐效果离线指标高就代表好？主动讲清离线 vs 在线的差距，说明你设计了曝光-反馈回流就是为了未来做线上验证——体现你懂评估的局限。
依赖开源主要靠 RecBole/Gorse/FFmpeg强调你的价值在工程集成与系统设计：把开源组件编排成可用系统、设计数据闭环、处理失败与幂等，而不是调包。
为什么不用微服务单体分层 + worker 拆分已满足当前规模；演进路径清晰（video-service 是独立服务，可拆分 recommendation 等），避免过度设计。
面试前必做 checklist
  • 能在白板上画出：上传→转码→向量化→推荐→训练闭环 的完整链路（含每步的数据落点）。
  • 能手写核心 SQL：SELECT ... ORDER BY embedding <=> $1 LIMIT 10（余弦距离）以及 pgvector 建索引语句。
  • 能讲清 BPR 损失公式和"为什么双塔适合召回"。
  • 能说清一个线上问题排查案例（比如：向量化某段一直失败 → 看 vector_stage 的 error_message/retry → 定位是 ASR 超时 → 调整超时/重试）。
